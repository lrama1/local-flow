# Implementation decisions

Deviations from, or clarifications of, [SPEC.md](../SPEC.md). Newest at the bottom of each milestone.

## M0 — Skeleton

1. **Capability method names.** Section 10.1 names every capability method `generate`. A single adapter class
   (e.g. `FakeAdapter`, later Wan for T2V + I2V) implements several capabilities, so methods are suffixed:
   `generate_t2i`, `edit`, `generate_t2v`, `generate_i2v`, `generate_flf2v`, `generate_ref2v`, `extend`,
   `synthesize`, `generate_v2a`, `generate_music` (`worker/adapters/base.py: CAPABILITY_METHODS`).
2. **Request schemas are shared, torch-free.** `worker/adapters/base.py` defines the Pydantic request models
   (Section 10.2). The API validates against them; the `/api/generate/*` bodies reference inputs by **asset id**
   and the dispatcher resolves ids to absolute paths at dispatch time (so retries re-resolve).
3. **Job params shape.** `jobs.params_json = {"adapter_key": ..., "request": {...}}`. The ModelCache/batching key
   is `(adapter_key, request.model_entry_id)`.
4. **Seeds are resolved at submit time** and stored in `params_json.request.seed`, so a retry reproduces the
   same output. Variations (M4) submit explicit different seeds.
5. **Retry creates a new job** with the same params instead of resetting the failed row (keeps history).
6. **Reorder** rewrites `priority` for the listed queued jobs so they run in the given order ahead of unlisted
   queued jobs. Queue order stays "priority desc, then FIFO" (ULIDs sort by creation time).
7. **Worker outputs** are written to `tmp/jobs/<job_id>/`; the API moves them into the project dir, probes them,
   makes thumbnails (first frame for video), and inserts `assets` rows. Step previews are numbered files in
   `tmp/previews/` (a file being served can't be replaced in place on Windows).
8. **Playground project.** Assets are project-scoped (Section 6.1), so Playground generations go into a project
   named "Playground", created on first use and remembered in `settings.playground_project_id`.
9. **Token transport.** `X-LocalFlow-Token` header everywhere, except where browsers can't set headers:
   `GET /api/files/*`, `GET /api/thumbs/*`, `GET /api/jobs/{id}/preview`, and `/ws/events` also accept
   `?token=`. The Host header must be a loopback name; WebSocket `Origin` must be the app's origin (or the Vite
   dev origin in dev mode). `?token=` values are redacted from logs, including uvicorn's access log.
10. **Dev token handoff.** `scripts/dev.mjs` generates the per-launch token and passes it to the backend
    (`LOCALFLOW_API_TOKEN`) and Vite (`VITE_LOCALFLOW_TOKEN`). In production the backend injects it into the
    served `index.html` as `<meta name="localflow-token">`.
11. **Dev proxy.** Vite proxies `/api` and `/ws` to the backend, so the browser is same-origin in dev too.
12. **Backend auto-reload in dev is done by `scripts/dev.mjs`**, not `uvicorn --reload`: on Windows uvicorn's
    reloader restarts the server with a console-wide `CTRL_C_EVENT`, which also kills Vite and interrupts the
    worker. The worker additionally ignores SIGINT (the supervisor owns its lifecycle) and exits if its parent
    dies.
13. **Event bus subscriptions remember their event loop** and `publish` hops loops with
    `call_soon_threadsafe`, so publishing from FastAPI's threadpool (sync endpoints) is safe.
14. **`httpx2` instead of `httpx`.** Starlette's TestClient deprecates `httpx` in favor of `httpx2` (pydantic's
    maintained successor). It's also the HTTP client for Civitai/downloads from M2 on.
15. **`psutil`** is added for RAM in `/api/system/status` (cross-platform, no torch in the API process).
16. **TypeScript 5.9**, not 7.x: `typescript-eslint` and `openapi-typescript` don't support TS 7 yet.
17. **openapi-typescript `--default-non-nullable false`**, so request fields with server defaults stay optional
    in generated types.
18. **shadcn/ui components are hand-written** in `src/components/ui/` (same Tailwind v4 + Radix approach,
    using the unified `radix-ui` package) rather than generated by the shadcn CLI.
19. **FakeEngine `extra` params** (`steps`, `step_delay_s`, `fail`, `crash`) make progress, failure, and
    worker-crash recovery testable; they're shown in the Playground's auto-generated Advanced form.

## M1 — Settings, secrets, LLM story pipeline

1. **API keys come from environment variables first** (user decision; SPEC §7.2 updated), then from keys
   pasted in Settings (OS keyring, or a Fernet-encrypted file when no keyring backend exists). On Windows a
   variable missing from the process environment is also read from `HKCU\Environment` / the system
   environment, so keys set after the terminal or IDE started still work. Tests use `secret_backend="memory"`
   and `secrets_from_env=false` so they never see real keys.
2. **Key validation is cached per key fingerprint** (12-char SHA-256 prefix) in the `settings` table. Listing
   LLM providers validates configured keys that are unchecked or older than 24 h. Unchecked keys count as
   usable; only keys that failed validation are skipped when picking a provider.
3. **LiteLLM call settings:** `drop_params=True` (GPT-5 reasoning models reject `temperature`); non-strict
   `json_schema` response format when LiteLLM reports support, else `json_object` (OpenAI/OpenRouter) or the
   in-prompt schema only; `reasoning_effort="low"` only for OpenAI-family reasoning models (for Anthropic it
   would turn on extended thinking); 3 attempts with backoff on 429/5xx/timeouts; errors map to stable codes
   (`llm_auth_failed`, `llm_timeout`, `llm_rate_limited`, `llm_invalid_output`, ...).
4. **Model lists and key checks use plain HTTP** (`httpx2`), not LiteLLM. The OpenAI list keeps models usable
   through Chat Completions (no codex/pro/realtime/audio/image), newest family first.
5. **Default models** (config, verified against the developer's accounts in Oct 2026): `openai/gpt-5.4-mini`,
   `anthropic/claude-sonnet-5`, `openrouter/anthropic/claude-sonnet-5`. Resolution per purpose: request
   override → Settings default for the purpose → `llm_purpose_models` in config → Settings "All story steps"
   → `default_llm_provider` → first usable provider (OpenAI, Anthropic, OpenRouter).
6. **Revisions are immutable rows.** Every step, manual edit, and restore creates a new revision (copying the
   other fields forward). "Diff before overwriting edits": when the refined story or bible was edited since it
   was generated, the UI re-runs the step with `dry_run=true`, shows a diff, and applies the proposal with
   `PATCH /story {…, applied_from}`. Restore brings back the idea/story/bible, not scenes and shots.
7. **Repair loop:** Pydantic validation plus semantic rules (Section 8.3) drive up to 2 repair turns. If
   semantic issues remain, the breakdown is auto-fixed (clamp to `max_clip_seconds`, adding `needs_extend`
   only when the overrun is more than 25% of a clip; fall back to a supported mode; drop unknown
   keys/speakers) and the fixes are reported as warnings. A total length outside ±15% of the target is a
   warning, not a repair trigger: with `gpt-5.4-mini`, repair turns for length rarely converged and doubled the
   cost. The prompt instead states the expected shot count. Totals count extensions as screen time.
8. **Render constraints** (Section 8.2) use the default catalog model's profile (5 s clips, `t2v` + `i2v`, no
   native audio, no FLF) until the model registry lands in M2 (see M2 #14).
9. **Bible → ingredients:** upserted by key; locked ingredients are never changed; unlocked bible ingredients
   that disappear from a new bible (and have no images) are removed. The bible style becomes one ingredient of
   kind `style` with the reserved key `style`. The breakdown and prompt rewrite see the *current* ingredient
   rows (so edits in the Ingredients tab and user-created characters apply), with the style from the bible.
10. **Extra shot columns** from the Breakdown schema: `needs_extend`, `extend_segments`, `continuity_notes`.
11. **Shots are created with `POST /scenes/{id}/shots`** (SPEC listed `POST /shots/{id}`). `POST
    /scenes/{id}/shots/reorder` may include shots from other scenes of the project, which moves them.
12. **Extra events:** `board.updated` and `ingredients.updated` (SPEC §14.3 updated).
13. **Cancelling LLM calls:** the UI aborts the request; the server polls `request.is_disconnected()` and
    cancels the LLM task (responds 499).
14. **Prompt templates** are one file per purpose/version with a `---- USER ----` separator between the system
    prompt and the user message. The first line is `PURPOSE: <name>`, which `FakeLLMProvider` routes on.
15. **Bible editing:** the Story tab offers a JSON editor for the whole bible; per-element editing lives in the
    Ingredients tab.

## M2 — Model management

1. **Catalog** (`services/registry/catalog.yaml`): 13 entries, each verified against the Hub on 2026-10-09
   (repo exists, every `allow_patterns` entry matches files, license URL resolves, size computed from
   `model_info(files_metadata=True)`). Each entry has one or more **parts** (repo + patterns): quantized
   transformers come from GGUF repos (`city96/FLUX.1-dev-gguf`, `QuantStack/*`), while text encoders, VAE and
   configs come from the official repo. Rows are upserted by `catalog_key` at startup. Install state, access
   and the license acknowledgement survive catalog edits. Entries removed from the catalog are dropped unless
   installed.
2. **Native-audio models (LTX-2 / HunyuanVideo 1.5) are not in the catalog yet.** diffusers isn't installed
   until M3, so support can't be verified (SPEC §9.2). LTX-2's repo is 314 GB of variants; a curated subset is
   picked in M4/M6. Wan VACE is listed as `experimental` (adapter in M7).
3. **Pickle-only models** (Kokoro-82M, MMAudio) are catalogued with `requires_pickle`. Install is refused
   until `allow_pickle_weights = true`; the UI explains why.
4. **HF layout:** `snapshot_download(local_dir=<hf_home>/repos/<org>--<name>, allow_patterns=<exact files>)`.
   It isn't the HF cache layout: files are plain and per repo, so deleting a model frees exactly its files.
   Entries that share a repo (FLUX Q8/Q4 share the gated base) only delete files no other installed entry
   uses. `HF_HOME` for the download process is `<data_dir>/models/hf`, so xet chunks and refs stay in the data
   dir.
5. **HF downloads run in a child process** (`python -m localflow.services.registry.hf_fetch`):
   - Cancel kills it; resume uses huggingface_hub's own `.incomplete` files. Verified on a real download: it
     cancelled at ~0.9 GB and resumed from 935.8 MB.
   - The token goes over stdin only (never argv/env). `HF_TOKEN` is removed from the child's environment and
     `token=False` is passed when none is configured.
   - The child exits when its stdin closes, so a dead API process leaves no orphan download.
   - Progress is measured by polling file sizes (final files + `.incomplete`), because hf_xet writes in bursts.
     Speed is averaged over a 6 s window.
6. **Default file selection** for an arbitrary repo:
   - Included: safetensors/gguf weights + configs/tokenizers.
   - Skipped: docs, media and alternative runtimes (`onnx/`, `openvino/`, `flax/`…).
   - Duplicates dropped: `x.safetensors` when `x.fp16.safetensors` exists; root single-file checkpoints when
     the repo has a diffusers layout (`model_index.json`); `.bin` pickles next to safetensors.
   - Code files are never downloaded; pickles need `allow_pickle_weights`. The user can change the selection.
7. **Access states** (SPEC §9.3), matched against real Hub responses in Oct 2026:
   - Public repos skip the check. With no token: `needs_token`.
   - Otherwise `auth_check(token=...)` decides:
     - 401 → `needs_token` ("token rejected").
     - `GatedRepoError` with "awaiting" → `pending_approval`; with "fine-grained" → `token_no_access`;
       otherwise → `license_not_accepted`.
     - `RepositoryNotFoundError` with a token → `token_no_access`.
   - An entry's access is the worst of its parts.
   - The `license_not_accepted` message names the signed-in account (SPEC §19).
   - Verified live: FLUX.1-dev → `ok` with the developer's token; `meta-llama/Llama-3.1-8B` →
     `license_not_accepted`; no token → `needs_token`.
8. **Civitai behavior** (verified against the live API, 2026-10):
   - Downloads 307-redirect to a signed R2 URL that honors `Range`. Early-access versions return
     `403 {"error":"Early Access"}` (→ `forbidden`). 401 → `needs_token` / `invalid_token`.
   - There's no explicit "login required" field. The lock badge comes from `paidAccess`/`availability`, and
     `usageControl != "Download"` means generation-only.
   - Install first probes the download URL (no body), so a login-required version fails immediately with a
     clear message instead of as a failed job.
   - The Bearer header is sent to `civitai.com` only, never to the CDN. HTML responses (by content type or by
     sniffing the first bytes) count as an auth failure and are never saved.
   - `sizeKB` is KiB. SHA-256 is verified after download.
9. **Civitai licenses:** Civitai has per-model permission flags rather than a license id. Entries store
   `license = "Civitai creator license (see permissions)"`, `license_url` = the model page, and the permission
   flags (shown in the browser and in the license dialog).
10. **URL/token hygiene** (SPEC §9.6):
    - Persisted URLs keep only Civitai's `type/format/size/fp` query params; signed redirect URLs are never
      stored.
    - Log redaction also strips signed query strings (`X-Amz-*`, `Signature`, `Expires`, `Key-Pair-Id`) and
      32-hex Civitai keys.
    - Tests assert no token appears in job params, registry rows or the log file. A real run was scanned the
      same way.
11. **`download_model` jobs run in the API process** (`DownloadRunner`, 2 at a time). They store only
    `{model_entry_id, name}`; tokens are resolved when the job starts.
    - `JobService` now has listener lists (`add_listener(on_change, on_cancel)`) so the GPU supervisor and the
      download runner both react to queue changes and cancels.
    - Cancelled or interrupted downloads leave `partial: true`. The card offers **Resume install** and
      **Delete** (which discards partial files).
12. **License acknowledgement** (SPEC §9.5) is enforced server-side: a generation that names a `model_entry_id`
    (or LoRA) fails with `409 license_not_acknowledged` (or `model_not_installed`) until acknowledged.
13. **Components have no capabilities:** VAE / text-encoder entries get `capabilities = []` even when an adapter
    is chosen, so they never satisfy a job type on their own.
14. **Render constraints** now come from the project's `default_video_model_id` when set (catalog `render`
    profile: max clip length, fps, supported modes). Otherwise the Wan 2.2 TI2V-5B default applies.
15. **Import existing Hugging Face login** reads `$HF_TOKEN_PATH`, then `$HF_HOME/token` (unless it's
    LocalFlow's own), then `~/.cache/huggingface/token`, and stores the token in the keyring. If `HF_TOKEN` is
    set, the environment still wins and the UI says so.
16. **New endpoints beyond SPEC §16:**
    - `GET /models/options`: adapter options with worker availability, hub accounts and free disk.
    - `POST /models/{id}/install` and `POST /models/{id}/check-access`: the catalog's install and "Check
      again" actions.

## M3 — Image generation

Verified on an RTX 5080 (16 GB, sm_120) with 24 GB of system RAM, of which only about 7 GB is usually free.
The stack is torch 2.14 + CUDA 13.0, diffusers 0.41 and transformers 5.19.

1. **The GPU stack is a default uv dependency group** (`gpu`, with torch from the `pytorch-cu130` index).
   `uv sync --no-group gpu` gives a CPU-only install. `engine = "auto"` (the new default) uses the real
   engine when torch sees a CUDA GPU; otherwise it uses the FakeEngine and reports why (`engine_note`, shown
   in the GPU chip). Adapter modules import diffusers lazily inside `load()`: importing it takes 15–19 s,
   while the worker itself starts in about 2 s.
2. **Weights stream straight to the GPU.** Copying them through system RAM doesn't fit on this machine:
   - diffusers' GGUF loader copies the whole file into RAM. Instead, `load_gguf_state_dict` builds tensors
     from the file's memmap directly on CUDA.
   - T5-XXL is about 11.5 GB in bf16, because transformers keeps `wo` in fp32. `load_t5_fp8` reads the
     safetensors one tensor at a time:
     - Linear weights are cast to `float8_e4m3fn` (norms and embeddings stay bf16). The result is about
       4.7 GB.
     - `apply_layerwise_casting` upcasts each layer during forward.
     - The fp32 cast inside `T5DenseGatedActDense` is patched out.
     - `dtype=` is always passed: accelerate's `set_module_tensor_to_device` otherwise casts to fp32.
3. **Flux placement** (`_FluxFamily.load`), chosen from free VRAM at load time:
   - **resident:** everything stays on the GPU.
   - **swap:** T5 is loaded only to encode a prompt that isn't cached yet, then freed. A 32-entry
     prompt-embedding cache is shared by Flux and Kontext.
   - **full_swap:** the transformer also leaves the GPU while T5 encodes; LoRAs are re-applied afterwards.

   `quality` forces resident, `balanced` takes resident only if it fits, and `low` swaps and tiles the VAE.
   The estimate counts measured **allocator overhead**: peak reserved minus peak allocated is about 2.5 GB,
   because GGUF layers dequantize on every forward. Without it, "resident" on 16 GB peaked at 16.2 GB reserved
   and spilled 2.2 GB into Windows' **sysmem fallback**. The driver doesn't raise OOM in that case; it just
   gets slower and uses system RAM. Measured at 1024², 28 steps:

   | Placement | Time per image | Peak reserved | Spilled to RAM |
   |---|---|---|---|
   | resident | 41.9 s | 16.2 GB | 2.2 GB |
   | swap (T5 reload included) | 40.4 s | 12.0 GB | 0.5 GB |

   So 16 GB cards use swap and 24 GB cards stay resident. The OOM retry with the next-lower profile is still
   there for Linux and for real OOMs.
4. **Model cache:** one heavy model at a time, keyed by (adapter, model entry, VRAM profile). LoRAs are
   swapped on the resident pipeline with `set_adapters` / `disable_lora`. `model_loaded`/`model_unloaded`
   events carry VRAM snapshots, and the worker records an idle baseline at startup. Measured unloads after
   Flux → Kontext and Flux → SDXL left 1419 MB used against a 1377 MB baseline.
5. **Kontext shares FLUX.1-dev's base:** its text encoders and VAE are byte-identical (same LFS sha256), so
   the Kontext entry downloads only the QuantStack Q4_K_M transformer and the Kontext configs. N references
   go on one horizontal **reference sheet** (white gutters, at most 2560 px wide). The prompt names each
   reference's position ("Mara (left), Brass lantern (right)") and asks for one new cinematic frame, not a
   collage.
6. **Keyframe composition:**
   - References are the primary images of the shot's ingredients plus the scene's location, ordered
     characters → props → location. At most 3 are used, since a wider sheet loses detail per reference.
   - `mode=auto` composes with the default image-edit model. With no references or no edit model, it falls
     back to T2I and returns a `note` that the panel shows. `mode=edit` fails instead of falling back.
   - Keyframe size comes from the project aspect ratio (16:9 → 1280×720).
   - Selecting a keyframe moves the shot `planned → keyframe_ready`; clearing it moves it back.
   - First/last-frame shots have separate start and end slots.
7. **Candidates are plain assets.** Their `generation_json.target_ref` is `{kind: "ingredient",
   ingredient_id}` or `{kind: "shot", shot_id, slot}`, and the asset list filters on it. There's no candidate
   table. Deleting an asset removes the candidate and clears any primary or selected keyframe pointing at it;
   a shot whose keyframe goes away returns to `planned`. The first finished candidate becomes an
   ingredient's primary if none is set.
8. **Default model:** a job without `model_entry_id` uses the project default, else the first installed
   catalog entry whose adapter can run the job type. Catalog order puts FLUX Q4 before SDXL. Under the
   FakeEngine, a named model runs on the `fake` adapter, but install and license checks still apply.
9. **License gate in the UI:** any generation that returns `409 license_not_acknowledged` opens the license
   dialog through one global `LicenseGate` and re-runs the request after acknowledgement. LoRAs are checked
   too.
10. **Uploads** (`POST /projects/{id}/assets/upload`, `POST /ingredients/{id}/assets`) check file content,
    not just the extension, and cap size at `max_upload_mb` (500). Ingredient uploads become the primary by
    default.
11. **Reproducibility:** each PNG embeds a `localflow` text chunk with prompt, seed, steps, guidance,
    scheduler, model, and LoRAs with weights. Seeds use a CPU generator, so the same seed and LoRA gave
    bit-identical output across worker restarts.
12. **Known limits:** SDXL's CLIP encoders truncate prompts at 77 tokens, and Flux ignores negative prompts.
    LoRAs on GGUF Flux transformers aren't verified on real weights yet; an SDXL LoRA (Civitai Detail Tweaker
    XL) is. Step-preview latent→RGB factors are approximate and affect only previews.
13. **Dev runner:** on Windows, `fs.watch` also fires on file access, so importing a module restarted the
    backend and killed in-flight GPU jobs. `scripts/dev.mjs` now restarts only when a `.py` file's mtime
    changes, or a file is added or deleted.
14. **Data dir on Windows:** `LOCALFLOW_DATA_DIR` falls back to the user environment in the registry, so a
    variable set with `setx` works in terminals that were already open (useful for keeping models on a
    bigger drive).

## M3.5 — Character creator

Verified on the RTX 5080 with FLUX Q4 (portraits, about 45 s) and FLUX Kontext Q4 (views and keyframes,
80–100 s each).

1. **Views:** the portrait stays in `ingredients.primary_asset_id`, so everything from M3 keeps working.
   `ingredient_assets` holds one chosen image per extra view (`full_body`, `three_view`, `side`, `back`,
   `face_closeup`), unique per ingredient+view. Candidates are still plain assets: `target_ref` gains `view`,
   and a candidate without a view counts as a portrait. The first finished candidate of a view is selected
   automatically. Deleting an asset clears its view and drops it from shot reference overrides.
2. **Wizard drafts are ingredient rows** with `draft = true` and a provisional key `draft-<10 chars>`, so
   generation, uploads and candidates reuse the ingredient endpoints unchanged. Drafts are hidden from
   ingredient lists (unless `include_drafts`), the story pipeline, mentions and references.
   - Saving is `PATCH {…, draft: false}`. The key is editable only while a draft; afterwards it's
     `409 key_immutable`, because prompts mention it.
   - Cancelling deletes the draft and its candidate images. Drafts older than 24 h are purged at startup.
   - The library wizard has no project, so it drafts in the Playground project, saves to the library, then
     deletes the draft.
3. **Portrait prompt:** when a character has an outfit, the portrait prompt says
   "Close-up head and shoulders portrait. {visual}, wearing {outfit}…". Every view is an edit of the
   portrait, so the portrait must already wear the outfit. Without it, FLUX invented clothes (the fisherman
   came out in a hoodie) and close-ups no longer matched wide shots. With the outfit placed before the
   framing, a long list (down to the boots) turned portraits into full-body shots, so the framing now leads.
   Bible characters without an outfit keep the M3 prompt.
4. **View instructions** are Kontext edits of the portrait at Kontext's ~1 MP resolutions (832×1248, or
   1392×752 for the turnaround). A 1568×672 sheet produced five figures; "exactly three figures: front, side
   profile, back" at 1392×752 produced three. Without an edit model, views fall back to text-to-image from
   the visual prompt + outfit, with a "lower consistency" note. SDXL + IP-Adapter isn't implemented.
5. **Reference selection by shot type** (`select_references`, at most 3):
   - Each character's first choice comes first: wide/establishing → full body, close-up → face close-up,
     otherwise the portrait. Then props, then the scene location, then the characters' second choices.
   - A character with several tiles gets labelled ones ("Mara (full body)").
   - `shots.reference_asset_ids_json` overrides the choice per shot; null means automatic. The shot panel
     saves the override in the same PATCH as its unsaved edits, because the panel remounts on every shot
     update.
6. **One character, several views ≠ several people.** With "full body (left), portrait (right)", the M3
   instruction "place them together in one scene" produced two copies of the fisherman. `edit_prompt` now
   gets who each reference shows and says "the images of Old Tom are different views of the same character;
   show Old Tom only once". The re-run had one Old Tom.
7. **Mentions** (`@key`, case-insensitive; `@@` is a literal `@`; `name@x.com` isn't a mention):
   - "Full" mode (keyframe, T2I, T2V, image edit) expands the first mention to "{name}, {visual prompt}"
     (a leading "A/An/The" is lowercased) and later mentions to the name. "Name" mode (I2V, FLF2V, extend)
     uses only the name, since the look comes from the keyframe. Speech, audio and music text is never
     touched.
   - Unknown keys are a `422 unknown_mention` at generation time, but saving a shot or an ingredient with one
     is allowed, and the editor warns inline.
   - Saving a shot adds mentioned ingredients to it, so they become references.
   - The raw prompt goes in job params `prompt_raw` (worker request models forbid extra fields) and into the
     asset's `generation_json.prompt_raw` / `mentions`.
   - Playground jobs (and prompts with no project) resolve against the Cast library.
   - The editor parses mentions client-side with the same regex as the backend, so warnings are instant.
     `POST /prompts/resolve` exists for previews and tests.
   - Escape in the suggestion list must not close the surrounding dialog. Radix dismisses on a document
     capture listener, so the textarea's own handler runs too late; a window capture listener marks the
     event `defaultPrevented`, which Radix respects.
8. **The Cast library holds snapshots.** A library character copies the fields and its images into
   `library/characters/<id>/`. Casting copies them back into the project as `imported` assets. Status is
   `synced`, `update_available` or `missing`, computed by comparing the library row's `updated_at` with the
   copy's `library_synced_at`. Sync stores the row's exact timestamp; an earlier 1 s "clock slack" hid edits
   made right after a sync. **Update from library** and **Push to library** overwrite explicitly, and the UI
   confirms. Key collisions get a suffix (`mara-2`). The `library.updated` event refreshes every project's
   ingredients, because badges depend on it.
9. **Story bible v2:** versioned templates are never edited in place, so `bible.v1` stays as it was and
   `bible.v2` adds voice hints and character info for existing characters. Locked, user-created and library
   characters keep their key and visual prompt through re-runs (acceptance 5), and their voice hints are
   only filled when empty.
10. **Voices are deferred to M6** (no voices table yet). `capabilities.voices` is false. The wizard records
    voice hints (gender/age/tone), `voice_id` is free text, and the cast block describes the voice from the
    hints.
11. **LLM helpers:** **Expand with AI** (`character_expand.v1`) turns a description, optionally starting
    from a template, into a full sheet. **Describe with AI** (`character_describe.v1`) needs a vision model:
    images go in as data URLs (at most 1024 px), and a non-vision model returns `409 llm_no_vision`. All
    three default models support vision.
12. **Templates:** 12 built-ins in `services/characters/templates.yaml`, two each for realistic, fantastical,
    sci-fi and historical, one each for anime, cartoon, creature and animal. User templates come from
    **Save as template**, with the primary image cropped to a 384 px thumbnail. Built-in thumbnails are
    rendered with FLUX by `scripts/characters/make_template_thumbnails.py`. That script adds a look per
    category ("photorealistic portrait photograph…", "anime illustration…"), because templates describe
    appearance only and the Playground has no style ingredient.
13. **YAML gotcha:** a flow mapping like `{tone: low, gravelly and slow}` splits at the commas, so every
    tone with a comma is quoted.

## M4 — Video generation

Verified on the RTX 5080 with Wan 2.2 TI2V-5B (QuantStack GGUF Q8_0) through the app API. The two A14B
entries and Wan 2.1 FLF2V are in the catalog and handled by the same adapter, but aren't verified on real
weights yet.

1. **Catalog: one text encoder for every Wan entry.** Wan 2.2 5B and A14B ship byte-identical bf16 UMT5
   encoders, and Wan 2.1 FLF2V's fp32 UMT5 is the same weights in fp32. That was checked by HTTP range reads
   of the safetensors, comparing after a bf16 cast. So the A14B and FLF2V entries take their `text` part
   from the 5B repo, and a second Wan model costs only its transformer.
   - TI2V-5B: the Q8_0 GGUF (5.4 GB) plus the diffusers base (VAE, scheduler, configs, UMT5), 19.7 GB in all.
   - A14B: the high- and low-noise Q4_K_M experts, 9.65 GB each.
   - FLF2V: city96's Q4_K_M (11.3 GB) plus the CLIP image encoder.
2. **Memory at 720p (1280×704, 121 frames = 27,280 tokens).** The first run spilled into system RAM: 14.5 GB
   dedicated plus 4.3 GB shared, and steps took minutes. There were two causes:
   - **TI2V embeds the timestep per token.** The conditioning frame gets t = 0 and every other token the
     step's t. diffusers keeps a (tokens × 6·3072) bf16 projection for the whole forward (1 GB), and every
     block adds all six fp32 modulation tensors at once (2 GB).
   - **The idle fp32 VAE** (2.7 GB) stayed on the GPU while denoising.

   The fixes:
   - **`wan_ti2v`** patches the transformer instance. It embeds each distinct timestep once (two at most)
     and gathers each modulation tensor only when a block uses it.
     - The block math is bit-exact against diffusers when given the same rows.
     - On real weights, whole-model outputs differ by 3% of the mean on random inputs. That comes from the
       time embedder running its GEMM on 2 rows instead of 3,510 (rows agree within 5e-4), amplified
       through 30 layers.
     - A tiny-model CPU test checks the patch against stock diffusers.
     - At 480p, peak activations dropped from 0.81 to 0.37 GB.
   - **The VAE waits on the CPU.** It moves to the GPU only to encode the conditioning image (wrapped
     around `prepare_latents`) and to decode. Pipelines report the device of their first non-CPU component,
     so they still run on CUDA.
   - **Decode checks free VRAM first** and drops the transformer if the decode won't fit. On Windows, sysmem
     fallback means an oversized decode doesn't raise OOM; it just gets several times slower.

   | Stage (720p, 121 frames) | Time | Peak allocated |
   |---|---|---|
   | UMT5 fp8 encode (new prompt) | 8.9 s | 7.05 GB |
   | Transformer load (GGUF memmap → GPU) | 3.5 s | 5.76 GB |
   | Denoise | ~18.5 s/step | 8.01 GB |
   | Decode (bf16, tiled) | 38 s | 9.95 GB |

3. **The VAE runs in bf16 with 384/320 tiles.** Measured on 41 real frames at 1280×704, with PSNR against
   fp32 at the default 256/192 tiles:

   | VAE | Tiles | Decode | Peak | PSNR |
   |---|---|---|---|---|
   | fp32 | 256/192 | 30.3 s | 2.12 GB | reference |
   | fp32 | 384/320 | 23.3 s | 3.84 GB | 48.0 dB |
   | bf16 | 256/192 | 16.2 s | 1.10 GB | 53.9 dB |
   | **bf16** | **384/320** | **12.6 s** | **2.00 GB** | **47.4 dB** |
   | bf16 | 512/448 | 11.1 s | 3.23 GB | 46.7 dB |

   Changing tile size alone already costs about 47 dB (the blend seams move), so bf16 is visually lossless.
   ComfyUI runs this VAE in bf16 as well. Latents are de-normalized in fp32 before the cast, and frames are
   converted to 8 bits in fp32, 16 at a time: bf16 can't hold 0–255 exactly after the scaling.
4. **Speed and defaults:**
   - A 5 s 720p take took 623 s at 30 steps through the API, including loads, decode and encode. The 4090
     figure Wan publishes (under 9 minutes at 50 steps) puts the 5080 with GGUF Q8 in the expected range.
   - The catalog default is 30 steps (Wan's reference uses 50, ComfyUI's template 20). The shot panel offers
     10–50 steps for drafts.
   - Frames are the shot's duration × the model's fps, snapped to 4k+1 (the VAE compresses time 4×) and
     capped at the model's clip: 121 frames at 24 fps = 5.04 s for TI2V-5B. Longer shots get a note and
     **Generate + extend**.
   - Size comes from the catalog's `sizes[vram_profile][aspect]`: 1280×704 in quality/balanced, 832×480 in
     low. Dimensions are multiples of 32, the VAE's 16× plus the 2× patch. Other aspect ratios use the 16:9
     area.
5. **A14B expert swap:** only one 9.65 GB expert is ever resident. The step callback releases the
   high-noise expert once the next timestep falls below the pipeline's boundary. `transformer_2` is a
   `_LazyExpert` proxy that loads the low-noise expert on first call. Loading it from the callback instead
   would briefly hold both experts, because the pipeline's loop keeps the current model in a local.
6. **Cancel:**
   - Forward pre-hooks on every transformer block and on the VAE decoder check the job's cancel flag. A 720p
     job was cancelled within 2.0 s (the driver polled every 2 s), without a worker restart.
   - If a job ignores cancel for `cancel_grace_s` (15 s), the supervisor kills the worker, marks the job
     cancelled and respawns the worker. A test checks this with a fake job that hangs.
   - Killing the worker mid-denoise failed the job with "The GPU worker crashed…" 2.3 s later. A new worker
     was idle after 4.4 s and ran the next job.
   - Windows exit codes are unsigned, so they're shown signed with hex: `-1 (0xFFFFFFFF)` for a killed
     worker instead of 4294967295, and `0xC0000005` for an access violation.
7. **Takes are plain video assets** with `target_ref {kind: shot, shot_id, slot: "video"}`, listed with
   `?shot_id=&slot=video`. Shot status is derived: a selected take means `video_ready` (`approved` is kept),
   else a keyframe means `keyframe_ready`, else `planned`. The first take is selected automatically, and an
   extension replaces the take it extended. Deleting a take clears it. Variations use consecutive seeds.
8. **Chained work lives in job params** (`chain`, never sent to the worker), and runs when the job's assets
   arrive: `extend` after a take ("Generate + extend"), and `select` + `video` after a keyframe ("Generate
   all" with auto-approve). Retrying a job keeps its chain. **Generate all** skips shots that have a take or
   a running job. Without auto-approve, it composes 2 keyframe options per shot and leaves the pick to you.
9. **Extend:**
   - Each segment is image-to-video from the previous clip's last frame, at the source take's size.
   - Each continuation drops its first frame, which repeats the previous last frame, and the result is
     joined in one ffmpeg pass (optional crossfade).
   - Measured on a 1-segment 720p extend: 241 frames (10.04 s). The frame-to-frame difference across the
     seam was 6.3, against 6.3–8.6 for its neighbours and a p95 of 14.3 over the whole clip, so the seam is
     invisible.
10. **Prompts:**
    - Image-to-video and first/last-frame prompts mention characters by name only, since the look comes from
      the keyframe. Text-to-video expands mentions fully and adds the style.
    - The camera move's fragment is appended, at the chosen intensity.
    - Wan's official default negative includes "static", which contradicts a "static camera" shot. The
      adapter now drops default-negative terms that the prompt itself uses (whole terms only), and static
      shots also negate camera movement.
    - This is a safeguard, not a measured fix. One 720p static take drifted into a handheld follow shot, but
      an A/B at 480p with the same seed kept the camera locked both with and without the change.
11. **Known limits:**
    - TI2V-5B conditions only on the first latent frame, so first/last-frame shots need the Wan 2.1 FLF2V
      entry. The 5B rejects them instead of ignoring the last frame.
    - Wan LoRAs aren't supported yet (`supports_lora = false`).
    - Video jobs have no step previews.
    - The panel's settings reset when the shot updates, because the panel remounts. Running jobs survive
      that: they're read from the jobs list.

## M5 — Timeline and export

Verified with six real Wan takes (1280×704 and 832×480 at 24 fps), exported through the UI, and with the
6-shot FakeEngine acceptance test.

1. **One `timelines` row per project.** `tracks_json` holds the whole Section 15.1 object (fps, size,
   tracks), validated by `TimelineData`. The schema allows exactly one video track and at most 3 audio
   tracks, with unique track and clip ids. The default has Video, Dialogue, Sound effects and Music, at 720p
   in the project's aspect ratio (16:9 → 1280×720, 9:16 → 720×1280).
2. **The server owns the video track's layout** (`services/timeline/model.normalize`):
   - Video clips sit on the timeline's frame grid. `start_s` is derived from order, trims and crossfades;
     the client's value is ignored.
   - Trims are clamped to the take's length, rounded down to a whole frame (a 121-frame take is
     5.041667 s).
   - A crossfade is at most half the shorter neighbouring clip, so a clip's two crossfades always fit
     inside it. A first-clip crossfade becomes a fade from black, and a cut has no duration.
   - Audio clips keep their own `start_s` (ms precision) and are sorted by it.
   - `PUT` returns the result with `notes` on what changed. The editor runs the same sequencing locally
     (`sequence` in `features/timeline/math.ts`), so layout is instant, and then adopts the server's
     answer.
3. **Exports are frame-exact** (`services/timeline/render.build_export`, a pure function with an
   exact-command test):
   - Each clip goes through `fps=N` then `trim=start_frame:end_frame`, so durations are whole frames.
     Cuts are pairwise `concat`, and crossfades are `xfade` at the frame offset where the incoming clip
     starts.
   - The output is trimmed to the expected frame count. A real-ffmpeg test checks it: mixed sizes and
     frame rates, a crossfade and a fade-in gave exactly the planned 108 frames.
   - A UI export of the check project had 737 frames for 30.708 s. Transitions match the plan: frame 0
     black, frame 6 half-faded, and a real blend mid-crossfade.
4. **Fit:** within 3% of the frame's aspect ratio, a clip is scaled and center-cropped instead of padded.
   Wan's 1280×704 loses 8 px rows rather than getting bars in 1280×720, and 832×480 crops slightly too.
   Anything else, such as a portrait clip in a landscape frame, is padded. The preview uses the same rule
   (`object-cover` or `object-contain`).
5. **Audio:**
   - Every audio clip, plus each video clip's own sound unless the video track is muted, is trimmed,
     converted to 48 kHz stereo, gained (clip + track dB) and delayed (`adelay … all=1`).
   - These are mixed with `amix normalize=0` (no level change by input count) over `anullsrc` of exactly
     the picture's length. So every export has an AAC track that ends with the video. `loudnorm` (-16
     LUFS) is optional.
   - Verified: a tone snapped to 10.042 s was silent (-91 dB) before and after, and present for exactly
     its 3 s.
6. **Exports run in the API process** (`ExportRunner`, like `DownloadRunner`):
   - One at a time. ffmpeg runs in a thread with `-progress`, and cancel kills it within 0.1 s (a test
     checks under 5 s). Shutdown marks the job failed ("Interrupted").
   - The job snapshots the timeline at submit, so later edits don't change a queued export.
   - The file becomes a video asset with `source="export"` under `projects/<id>/exports/<asset_id>.mp4`,
     thumbnailed 1 s in (exports usually open with a fade from black).
   - Export history is `GET /assets?source=export`. A 30 s 720p export took about 4 s.
7. **Auto-assemble:**
   - It uses every shot's selected take, in full: trims are a timeline edit, and a planned 4 s shot whose
     take was extended to 10 s keeps 10 s.
   - Shots within a scene are cut; scenes are joined with a 0.5 s crossfade, and the first shot fades in
     from black. These are options in the body.
   - Shots without a take are skipped and listed. The music track is kept.
   - Shots' selected audio lands on Dialogue (TTS), Sound effects (V2A or uploads) or Music, at the clip's
     start. That gets real content in M6.
   - Deleting an asset removes its clips, and the next load ripples the video track (`timeline.updated`).
8. **Editor:**
   - **Edits apply locally at once.** Saves are debounced by 500 ms and serialized through one promise
     chain, so PUTs never race. The server's answer replaces the draft only if nothing changed meanwhile.
     Pending edits are flushed before export, auto-assemble and leaving the tab.
   - **Pointer handlers are stable.** They read the latest state through a ref, so memoized clips don't
     re-render on every playback frame.
   - **Dragging:** a video clip drops at the index of the other clips' centres. Trims and audio moves snap
     to clip edges, the playhead and 0 within 8 px (an amber guide line shows it), then to the frame grid
     (video) or ms (audio).
   - **Keyboard:** Space plays or pauses (unless a button has focus, which handles Space itself). ←/→
     step a frame, Shift steps a second, Delete removes the clip, and Home/End jump. Inputs and dialogs
     are ignored.
9. **Preview** (approximate, as the spec allows):
   - One `requestAnimationFrame` clock drives the playhead. Media elements follow it, so gaps, cuts and
     audio offsets line up without chaining `ended` events.
   - The previous (during a crossfade), current and next clips are mounted. The next one waits at its in
     point, so a cut doesn't wait for a load.
   - Fades are opacity ramps over black.
   - Drift is corrected by nudging `playbackRate` (±10%) and only re-seeking beyond 0.5 s. Re-seeking a
     playing video stalls it, which then looks like more drift.
   - HTML volume caps at 1, so boosts above 0 dB are heard only in the export.

## M6 — Audio

Verified on the RTX 5080 with Kokoro-82M, MMAudio large 44.1 kHz v2, MusicGen small and a real LLM
(project "Audio check (M6)"), and with FakeEngine tests for every endpoint.

1. **Dependencies** (`pyproject.toml`, `gpu` group):
   - `kokoro` with its English G2P (`misaki[en]`: spaCy plus a bundled espeak-ng). spaCy's
     `en_core_web_sm` is pinned as a URL dependency, because misaki otherwise pip-installs it at run time,
     which fails in a uv venv.
   - `mmaudio` is a git dependency pinned to a commit. Its own requirements cover training and its Gradio
     demo (gradio, tensorboard, hydra, opencv, av, torchcodec, …). `[tool.uv] override-dependencies` drops
     them with never-true markers and relaxes its `numpy<2.1` pin, so numpy stays at 2.5.3 (numba 0.68 is
     fine with it). `python-dotenv` stays, since pydantic-settings needs it.
   - `torchvision` comes from the cu130 index. torchaudio isn't used: cu130 wheels stop at 2.11, and
     nothing on the inference paths imports it.
2. **Voices** (`voices` table, `services/voices.py`):
   - Built-ins come from each TTS adapter's `AdapterInfo.voices`. They're upserted by (adapter, native id),
     so their ids stay stable, for every adapter the worker can run with an installed model (the FakeEngine
     needs none). Sync is lazy: the first list after the adapter set changes. Voices of an adapter that
     went away stay, marked unavailable, because characters may use them.
   - A custom voice is a built-in base voice plus `VoiceParams`: up to two other voices blended in, a base
     weight, and a pace (0.7–1.4). Blend voices must share the base voice's language family; English
     accents mix.
   - Characters and Cast library entries store a `voices.id`, validated on write. Deleting a custom voice
     unassigns it everywhere. The TTS request carries the native voice and params (`resolve_tts` also
     accepts LocalFlow ids on `POST /generate/tts`).
   - Previews are cached as `library/voices/<id>/preview.wav`, keyed by their text. Changing a voice's
     sound drops the cache. `GET …/preview.wav` accepts `?token=` for `<audio>`. Auditioning unsaved
     settings is a plain TTS job; the UI plays its asset.
3. **Kokoro** (`worker/adapters/kokoro.py`):
   - Loaded from the catalog files: `KModel(config=, model=)`, one `KPipeline` per language sharing it, and
     style packs read from `voices/*.pt`. Nothing downloads at run time.
   - A blend is a weighted average of style packs, which is what Kokoro's own `"a,b"` voice mixing does.
   - Grades come from the model card; the short trait descriptions are ours (used for suggestions and
     design). Japanese and Mandarin are left out, since they need extra G2P packages. That leaves 41 voices
     in 7 languages.
   - Kokoro pads every utterance with about 0.3 s of silence before and 0.5 s after, so lines are trimmed
     to a 30/80 ms pad and the layout sets the timing. Its output peaks at only 0.28–0.42, so lines are
     raised to -1 dBFS (at most 4×).
   - The first job takes about 12 s (load plus spaCy); later ones about 2 s.
4. **Voice design** (`POST /voices/design`, LLM purpose `voice_design`): Kokoro can't follow a text
   description, so the LLM picks a blend and pace from the base voice and same-language voices, given
   their grades and traits. Unknown voice ids are dropped with a warning. A real run (gpt-5.4-mini, 2–3 s)
   turned "a weathered old fisherman; gravelly, slow and kind" into George 0.8 + Lewis 0.12 + Fable 0.08
   at 0.86×.
5. **Dialogue is one TTS job per shot** (`SpeechAdapter.synthesize`, `lines` mode), producing one WAV as
   long as the clip:
   - Each line uses its speaker's voice and params. Lines follow each other after a 0.3 s lead-in and
     0.35 s gaps.
   - If they don't fit, the lead-in and gaps shrink (to 0.1/0.15 s) first, then the pace goes up, to at
     most 1.15× (`fit: "speed"`).
   - Anything still too long is kept rather than cut. The WAV runs past the clip, and
     `generation.output.overflow_s` drives a "+0.8 s" warning. Line placements are kept there too.
   - The plan (`POST /shots/{id}/audio-plan`) estimates 2.6 words/s at the pace it'll use, including a
     custom voice's own pace. Measured: about 2.5 words/s for George.
   - Kokoro has no emotion control, so an emotion only nudges the pace (e.g. excited 1.08×, sad 0.92×).
   - A speaker without a voice, or whose voice's model isn't installed, gets a suggestion from their
     voice hints, avoiding voices other characters already use; the narrator gets a calm one. The plan
     says so.
   - Voices from two TTS models in one shot is a 409.
6. **Selection and the timeline:**
   - A finished dialogue or SFX take becomes the shot's selected audio for its part. The part comes from
     the job's target slot, else its type, and `select-audio` switches between takes.
   - If the timeline already holds the shot's take, the shot's clip on the Dialogue or SFX track is
     swapped in place, aligned with the take and trimmed like it. So new audio needs no re-assemble, which
     would drop edits.
   - Auto-assemble (M5) places selected audio as before.
7. **MMAudio** (`worker/adapters/mmaudio.py`):
   - It uses MMAudio's model classes but not `eval_utils`, which imports the dropped training packages.
     `generate` follows MMAudio's own.
   - Frames come from our ffmpeg, matching MMAudio's transforms: 8 fps squashed to 384² for CLIP, and 25
     fps with the short side at 224 and a center crop for Synchformer.
   - MMAudio fetches CLIP and BigVGAN from the Hub by name. The catalog entry now includes both as parts
     (10.7 GB in all), and they're pointed at the local folders while the model loads: open_clip's
     `local-dir:`, and BigVGAN's `_from_pretrained` on the folder.
   - bf16: 4.75 GB allocated, about 27 s to load, then 25 steps in about 3 s for a 5 s take.
   - Whole 8 fps CLIP frames bound what it sees (5.04 s gives 40 frames, 5.0 s), so the output is padded
     to the take's exact length with a 20 ms fade.
   - It's trained on 8 s clips. Up to 10 s is one pass; longer takes use roughly 8 s windows starting on
     whole seconds (where the two frame grids meet), overlapping by at least 1 s. Each overlap gets a 1 s
     equal-power crossfade at its middle; averaging two independent generations would sound phasey.
     Verified on 15.08 s: 3 windows, exact length, 39 s, and smooth levels at both crossfades.
   - The default SFX negative prompt is "speech, talking, voice, music", minus words the prompt itself
     uses.
8. **Music** (`POST /projects/{id}/generate-music`):
   - MusicGen small runs through transformers in fp32, at 32 kHz mono.
   - The prompt is the scene's or film's music cues (plus the style notes), unless one is given. The
     length is the timeline's, else the shots' takes.
   - Adapters declare `max_duration_s`: MusicGen makes up to 30 s, and the response notes the cap. A 12 s
     piece took 15 s.
   - The result is placed on the Music track at the film's or scene's start.
   - ACE-Step still has no adapter.
9. **Acceptance** (`m6_accept.py` against the real server):
   - A 5.04 s shot with one line plus an SFX prompt, and a 10.04 s shot with two speakers, each produced a
     dialogue and an SFX WAV matching their clip within 0.4 ms.
   - Auto-assemble, music, then export gave AAC 48 kHz stereo, 15.08 s long, with the dialogue window
     5.5 dB above the SFX-only stretch after it.
   - The designed "Old Tom" voice was auditioned, assigned, and used: the TTS request carried bm_george
     plus its blend.
10. **Limits:**
    - No lip-sync, and no native audio (Wan 5B has none).
    - The ModelCache holds one model, so dialogue followed by SFX reloads MMAudio (about 27 s) after
      Kokoro.
    - Kokoro and MMAudio need `allow_pickle_weights = true`. Their weights are loaded with
      `torch.load(weights_only=True)`.

## M7 — Polish

Verified on the real data dir (RTX 5080): the library on "Audio check (M6)", vision review with
gpt-5.4-mini on "Harbor Keeper (M3.5 check)" and "Harbor Lantern", Diagnostics, and the Playwright smoke
test. Test data made along the way was removed.

1. **Collections** (`collections`, `collection_assets`, migration 0007):
   - Per project, with unique names (409 `collection_exists`). An asset can be in any number of them.
     Deleting an asset or a collection cascades to the memberships (bulk SQL deletes, not ORM deletes of rows
     the FK cascade already removed). Only assets of the same project can be added.
   - The cover is the newest member with a thumbnail. Changes publish `collections.updated`.
2. **Library queries** (`GET /projects/{id}/assets`):
   - Type, source, favorite and collection are SQL filters. Tag, model, scene, ingredient and search read
     `generation_json` in Python, which is portable and fine at a project's scale (hundreds to a few
     thousand assets). `GET …/assets/facets` returns the counts the filter menus show.
   - `model` matches the model entry id, or the model name for assets made before entries had ids.
     `scene_id` matches assets made for any shot of the scene. `featuring` (an ingredient) matches its
     candidates, prompts that @mention it, and assets made for shots it's in.
   - Search covers the prompt, the raw prompt with @mentions, speech text, dialogue lines, the uploaded
     file name, the model name and tags.
   - `POST /projects/{id}/assets/bulk` tags, untags, favorites or deletes up to 500 assets in one call and
     publishes one `assets.updated` (or the delete events).
3. **Uploads are normalized** (Section 13): video that isn't H.264/yuv420p is re-encoded (libx264 CRF 18,
   AAC audio), H.264 in another container (MOV, MKV) is remuxed without re-encoding, and MP3/FLAC/OGG become
   16-bit WAV. WAV, M4A and AAC are kept. `generation.normalized` records what happened, e.g.
   "webm/vp9 → mp4/h264". Re-encoding scales odd sizes down to even ones (yuv420p H.264 needs them). A
   failed conversion is a 422 `convert_failed`, and the upload and any partial output are deleted.
   Ingesting runs off the event loop (`asyncio.to_thread`).
4. **Frame extraction** (`POST /assets/{id}/extract-frame`) snaps the time to the take's frame grid and
   clamps it to the last frame. ffmpeg seeks half a frame early: with an accurate input seek it drops
   frames before the (millisecond-rounded) time, so 1/24 s ("0.042") would have returned frame 2 for
   frame 1, about half the frames at 24 and 30 fps. A test checks frame colors. The image is a normal
   asset (`source: extracted`) with the video as its parent. In the drawer, "Use as keyframe/reference" on a
   video extracts the frame under the playhead first. Saved frames show inline, because a toast's action
   button can't be clicked behind a modal.
5. **Reuse settings** maps an asset's `generation` back to the Playground form (`features/assets/reuse.ts`):
   kind from the job type, the prompt, the seed the output actually used, the size preset with the nearest
   aspect ratio, duration and fps, model, LoRAs, extra params and input assets. Playground outputs keep
   their raw prompt with @mentions (Cast library keys, which the Playground resolves again). Project
   assets (with a `target_ref`) use the prompt as sent: their mentions are project keys the Playground
   would reject, and the sent prompt includes the camera move, style and cast details. It travels through
   the UI store, and the Playground reads it once. Inputs from another project are shown (and allowed:
   Playground requests resolve assets by id).
6. **Vision review** (`POST /shots/{id}/review`, purpose `vision_review`, `vision_review.v1.j2`):
   - Reviews the selected keyframe (default) or any image or take of the shot. A take is reviewed at 30%
     and 70% of its length (early and late drift). Images are sent as JPEG data URLs of at most 1024 px.
   - The references are exactly what keyframes use (`references_for(...).selected`: the shot-type-aware
     views, or the user's override), with each ingredient's visual and outfit prompt as text.
   - The answer is `{consistent, issues[], suggested_prompt_fix}`. A semantic check asks for a repair when
     it says inconsistent without issues or a fix. The fix replaces the field it targets (keyframe, end
     frame or video prompt) and keeps @mentions; the template forbids adding new ones (a real run had
     turned "Mara" into "@Mara").
   - `GET /llm/vision?purpose=` reports whether the purpose's model can read images; the button is
     disabled with the reason otherwise. The check saves the panel's draft first, which remounts the panel
     (it's keyed on the shot's `updated_at`), so the result, pending state and error live in the
     TanStack Query caches, keyed by shot and asset, not in component state. Real runs: 3–4 s and $0.003–0.005 per check. It correctly passed
     Old Tom's keyframe and take and flagged a product shot of a lantern as missing Mara, the pier and the
     dusk light.
7. **Diagnostics** (`GET /system/diagnostics`, `GET /system/logs/{name}`, `GET /system/diagnostics/bundle`):
   - Checks: a write/read/delete test in the data dir, disk space (warns under 20 GB), ffmpeg/ffprobe,
     nvidia-smi, PyTorch + CUDA as the worker sees it, worker state, the secret store's backend name (e.g.
     "Windows WinVaultKeyring"), and LLM providers. Each failure says how to fix it.
   - The worker reports torch, CUDA, cuDNN and the device in its `ready` event, only if torch is already
     loaded, so the FakeEngine never imports it. `SystemStatus.cuda_version`/`cuda_available` come from there.
   - Folder sizes walk the tree without following links (the HF cache links snapshots to blobs) and are
     cached for a minute; `?refresh=true` recounts. About 80 ms for 60 GB of models.
   - Log tails only serve files listed in `logs/`, formatted from the JSON records and redacted again. The
     bundle (checks, status, `config.toml`, the last 5000 lines of each current log) is redacted and has no
     media, database or key files. A scan of a real bundle found none of this machine's 12 secret values.
     The UI downloads it with `fetch` and a blob URL, so no new `?token=` route was needed.
8. **`fake_llm` mode** (config, `LOCALFLOW_FAKE_LLM`): `FakeLLMProvider` with canned responses for every
   purpose (`services/llm/demo.py`, also the tests' fixtures) answers as OpenAI. No key is read, statuses
   show it as configured with source `fake`, and Diagnostics warns that it's on. It's for offline demos and
   the smoke test.
9. **Playwright smoke test** (`frontend/e2e/`, `npm run test:e2e`):
   - `e2e/serve.mjs` starts the real server on port 8799 with a fresh temp data dir, the FakeEngine,
     `fake_llm`, and no env keys or keyring, serving the built `dist/`.
   - The test creates a project, then runs refine, bible and breakdown (5 shots), Generate all with
     auto-approved keyframes, waits until every shot has a take, then auto-assembles, exports and checks the
     export in the library. About 15 s.
   - It's separate from `npm test`, which stays fast and needs no browser.
10. **Limits:** search is a substring match (no ranking or full-text index). Vision review looks at stills,
    so it can't judge motion. The bundle includes `config.toml` as written (redacted), which may include
    local paths.

## In-app tutorials

1. **Static files, no API:** videos, captions, posters and `index.json` live in
   `frontend/public/tutorials/`. Vite serves them in dev; the production SPA route serves them from
   `dist/`, with correct MIME types and Range support for seeking. They need no token. The page treats a
   missing manifest (the SPA fallback answers with HTML) as "no tutorials yet".
2. **Recorded from the real app** by `scripts/tutorials/make_tutorials.py`, a self-contained uv script
   (PEP 723 dependencies, so the backend lockfile is untouched):
   - Narration is synthesized first, so every step knows its length. Narration never overlaps a time-lapse.
   - **Capture uses the DevTools screencast rather than Playwright's `record_video`.** Playwright's VP8
     encode (about 0.7 Mbit/s) measured 31 dB PSNR against a screenshot, and the UI text looked soft. The
     screencast gives JPEG q92 frames with timestamps, and the encoded MP4 scores about 50 dB against them.
   - The screencast ignores Playwright's emulated device pixel ratio, so Chrome runs with a real
     `--force-device-scale-factor=1.5`. The window is resized over CDP until the viewport is 1280×720, which
     yields a 1280×720 layout captured at 1080p.
   - **Waits are time-lapsed** (LLM steps, GPU jobs) to 2.5–6 s each. A badge shows the real elapsed time.
     Every frame's timestamp is remapped onto the edited timeline in one ffmpeg concat list. Per-segment
     `trim` filters were dropped: each segment ended at its last changed frame, and splitting one input into
     many trims buffers frames in RAM.
   - A drawn cursor (DOM overlay) shows pointer moves and clicks, since headless Chrome draws none.
3. **Narration voice:** edge-tts `en-US-AndrewMultilingualNeural`. edge-tts calls Microsoft's online
   Edge TTS service, so only the fixed narration script leaves the machine. Sentence boundaries from the
   service become WebVTT cues, and long sentences are split into timed chunks.
4. **The full-film tutorial** ("Make a film, start to finish") runs the whole pipeline for real: a
   15-second project, references, keyframes, Wan video, voices, SFX, music, timeline and export. It takes
   about an hour of GPU time.
   - Only the hero's reference and one dialogue and SFX clip are generated on screen. The rest go through
     the API under a time-lapse, so the video stays about 5 minutes long.
   - **Chrome runs with `--disable-gpu`.** Headless Chrome's GPU compositing of a constantly repainting
     screencast competed with Wan for VRAM and made video generation about 4× slower.
   - The screencast has no audio, so the finished export's soundtrack is mixed in under the narration
     while the film plays.
   - uvicorn's 5 s keep-alive timeout matches the 5 s poll interval and sometimes resets a connection, so
     the recorder retries GET requests.
   - Rehearse the flow against the FakeEngine and fake-LLM server (`E2E_PORT=8799 node e2e/serve.mjs`,
     then `--base-url http://127.0.0.1:8799`). It runs in about 5 minutes and skips the waits for real
     jobs.
